# AgentOS Backend Architecture Boundaries

Updated: 2026-05-31
Status: Stage 0 architecture freeze; federation removed from current roadmap on 2026-05-31

This document defines the boundaries that should remain stable while AgentOS Backend moves from current M3.5 foundation toward full platform completion.

## 1. Boundary Principles

1. Keep business orchestration in Go.
2. Expose Rust capabilities only through narrow, stable, tested FFI exports.
3. Treat PostgreSQL as the source of truth for structured business state.
4. Treat Redis as runtime support, not business truth.
5. Treat MinIO as the only object storage implementation for the current platform phase.
6. Treat security/governance/audit as platform control planes, not feature-specific afterthoughts.
7. Prefer durable queues in PostgreSQL for business-auditable work.
8. Make every external execution surface policy-gated and auditable.
9. Do not fake semantic, policy, or billing success when a subsystem is unavailable.
10. Keep Federation / multi-server networking out of the current roadmap; do not introduce server discovery, remote trust, or cross-server data synchronization yet.

## 2. Go vs Rust Boundary

### Decision

Go is the AgentOS Backend service runtime and owns:

- HTTP routing;
- WebSocket lifecycle;
- service orchestration;
- persistence transactions;
- admission policy;
- device pairing;
- sync event recording;
- KB Hub publishing/access/billing/search orchestration;
- future SAGE, plugin marketplace, admin APIs, governance, and audit orchestration.

Rust SDK is integrated only through explicitly exported FFI functions. Current verified FFI surfaces:

- `agentos_identity_verify_ed25519_challenge`;
- `agentos_apply_knowledge_sync_events_json`;
- `agentos_apply_knowledge_sync_pull_response_json`.

### Rules

- No new Rust capability may enter backend runtime without an `agentos-ffi` C ABI contract and tests.
- FFI functions must not hold backend business state.
- FFI functions must return explicit errors and provide safe string/free semantics.
- Backend startup must fail if required runtime FFI symbols for configured verifier cannot load.
- SDK/client reducer FFI can be contract-tested from backend, but backend business writes remain Go-native.

## 3. Identity Boundary

### Current decision

- User identity is based on Ed25519 public keys.
- Authentication uses challenge-response followed by JWT issuance.
- Direct registration is disabled.
- New users pass through admission policy during auth verification.
- New devices join through QR-only pairing.

### Platform completion rules

- Manual pairing-token entry remains out of product scope.
- Device revoke/rename/trust must be represented as auditable domain actions.
- Sensitive operations must require fresh confirmation once password confirmation is implemented.
- Admin bootstrap must prevent accidental permanent lockout.

## 4. Sync Boundary

### Current decision

- Cross-device sync uses a backend-owned event stream in PostgreSQL.
- Sequences are monotonic per user.
- Pull/ack is the canonical sync path.
- WebSocket `sync.event` is only a real-time hint.
- Domain-specific write APIs create sync events; there is no generic external sync write endpoint.

### Platform completion rules

- New sync object families must be added to `sync-contract.md` and tested.
- Event schema breaking changes require schema version bump and client compatibility notes.
- Idempotency remains based on non-empty `(user_id, client_event_id)` uniqueness.
- Generic external sync writes remain out of scope until a governance/policy boundary exists.
- Full client merge engines are client/SDK concerns; backend must provide stable envelopes and fixtures.

## 5. Storage Boundary

### PostgreSQL

PostgreSQL owns:

- identity records;
- devices;
- challenges;
- admission records;
- conversations/messages/offline messages;
- sync events/cursors/sequences;
- personal knowledge entries;
- object metadata;
- KB Hub collections/snapshots/subscriptions/usage/billing/search docs/embedding jobs/embedding vectors;
- future plugins/SAGE/audit/admin/job records.

### Redis

Redis is allowed for:

- runtime cache;
- rate limiting;
- presence/online state;
- ephemeral performance support.

Redis must not be the sole truth source for:

- payments;
- plugin execution reports;
- sync events;
- embedding jobs;
- audit events;
- permissions.

### MinIO

MinIO is the only object storage provider in the current architecture.

MinIO stores:

- uploaded objects;
- KB snapshot manifests;
- KB snapshot entry Markdown;
- future plugin packages/icons;
- export/import archives;
- large attachments.

Rules:

- Clients never receive MinIO root/access keys.
- Clients access objects only through backend-authenticated presigned URLs or backend proxy paths.
- Object keys are generated by the backend, not trusted from clients.
- `object_records` is the authority for ownership, scope, status, hashes, sizes, and references.
- Buckets default to private.

## 6. Embedding and Search Boundary

### Current decision

- Lexical/search metadata is stored in PostgreSQL.
- Semantic vectors use PostgreSQL + pgvector.
- Default model target is BAAI/bge-m3 with 1024-dimensional dense vectors.
- Go API server does not load ML models.
- A Python HTTP embedding worker owns model inference.
- A Go embedding job worker owns durable queue consumption and database writes.

### Rules

- Snapshot publishing must not synchronously block on model inference.
- Semantic unavailable must be explicit.
- Hybrid search must degrade to lexical when semantic is unavailable.
- Ordinary Go tests use deterministic embedding provider and must not download real models.
- Real BGE-M3 smoke is operational validation, not standard unit CI.
- Chunk-level search must add new chunk tables/jobs; do not overload entry-level embedding semantics.

## 7. KB Hub Boundary

### Current decision

KB Hub is server-hosted snapshot publishing:

- local personal knowledge entries can be published into immutable snapshots;
- PostgreSQL stores metadata and indexes;
- MinIO stores large content objects;
- subscriptions reference collections/snapshots;
- billing records usage and ledger foundation.

### Rules

- Published snapshots are immutable.
- Updating a collection creates new snapshot versions rather than mutating old content.
- Installed content access is gated by active subscription or future entitlement policy.
- Public metadata is separate from private/full content access.
- Public marketplace visibility requires a published collection with approved review state.
- Stage 2 moderation includes review/takedown/report records, but reviewer role policy and moderation dashboard remain future admin work.
- Snapshot versions are immutable; lifecycle operations archive/restore snapshot availability rather than mutating snapshot contents.

## 8. Plugin and SAGE Boundary

### Decision

AgentOS Backend will coordinate SAGE plugin execution but will not execute arbitrary plugin code in the service process.

The server owns:

- plugin registry;
- version/package metadata;
- manifest validation;
- review workflow;
- installation and capability grants;
- flow definition generation;
- execution report ingestion;
- policy decisions;
- usage and billing records;
- audit trail.

The client/Agent runtime owns:

- local device actions;
- UI presentation;
- user confirmation interaction;
- local execution of approved client-side steps.

### Rules

- No plugin bypasses the governance/policy engine.
- Approved manifest does not imply unconditional execution permission.
- Every flow creation must record policy decision context.
- Execution reports must be idempotent and auditable.
- High-risk capabilities require explicit approval gates.
- Any future remote plugin concept is out of scope for now and must not bypass local server policy if it is ever reintroduced.

## 9. Governance Boundary

### Decision

AgentOS needs a platform-wide governance plane before broad SAGE, high-risk tool, billing, object, and admin execution.

Governance owns:

- capability taxonomy;
- risk levels;
- policy decisions;
- tool definition scanning;
- response inspection;
- approval receipts;
- audit events;
- kill switches;
- security incidents.

### Rules

- Prompt instructions are not a security boundary.
- Model-selected tool calls are not trusted until policy-evaluated.
- Approval should be fresh for risky actions unless a specific durable grant exists.
- Enterprise/admin deny policies must not be overridden by ordinary user approval.
- Sensitive outputs must be inspected before being returned to agent context where applicable.

## 10. Billing Boundary

### Current decision

Billing foundation exists as internal ledger records:

- `billing_accounts`;
- `billing_transactions`;
- `kb_usage_records`;
- `contributor_earnings`.

### Rules

- Backend ledger is source of truth for internal usage and balances.
- External payment processors, if added, are adapters around ledger events.
- Usage metering must be idempotent.
- Pricing changes must be versioned or auditable.
- Plugin and KB billing should share ledger primitives but keep domain-specific usage records.

## 11. Deferred Scope: Federation / Multi-Server Networking

### Decision

Federation / multi-server networking is removed from the current architecture and roadmap. The existing `user_server_connections` / `/api/v1/servers` capability remains only a local user configuration object that can be synced across the same user's devices. It does not imply server-to-server trust, remote authentication, or cross-server data synchronization.

Not in current scope:

- server identity and public key discovery;
- `.well-known/agentos-server.json`;
- federation capability discovery;
- signed server handshakes;
- remote server trust scores;
- remote plugin metadata discovery;
- remote install references for plugin/server resources;
- Federated KB Discovery / remote KB metadata discovery;
- cross-server strong consistency;
- hidden remote database writes;
- global timeline requiring multiple servers to agree;
- remote content access based on cross-server authorization.

Reopening rule: Federation can only be reconsidered after a separate product/security review, and only after single-server governance, audit, policy, kill switch, and approval primitives are mature.

## 12. Admin and Observability Boundary

### Current state

- `/health` checks database, Redis, and identity verifier.
- Admin routes exist for admission only.
- Logging uses standard logging.

### Platform completion rules

- Add `/ready` separately from `/health`.
- Add request IDs and structured logs.
- Add admin APIs for jobs, audit, security, plugins, KB moderation, and billing.
- Add release gates that validate migrations, smoke tests, and security invariants.
- Do not rely only on unit tests for deployment-critical flows.

## 13. Background Job Boundary

### Current state

- Embedding jobs use `kb_embedding_jobs` as a durable PostgreSQL queue.

### Platform completion rules

- Keep business-auditable jobs in PostgreSQL.
- Add a unified background job model only if it improves operational consistency.
- Job handlers must be idempotent where possible.
- Failed jobs need retry/backoff metadata and admin retry APIs.
- Redis may optimize scheduling but must not replace PostgreSQL as the truth source for critical jobs.

## 14. Non-Goals To Preserve

- No Rust sidecar in the current backend architecture.
- No gRPC sidecar as current Go ↔ Rust integration path.
- No external object storage adapters in the current phase.
- No default closed/paid embedding provider dependency.
- No fake semantic search success.
- No generic external sync write endpoint without governance.
- No arbitrary plugin code execution in the Go API process.
- No cross-server database replication.
- No Federation / multi-server networking in the current roadmap.
